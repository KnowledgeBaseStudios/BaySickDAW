## 2026-06-01 — Task 1 — int-sample transport + sample-accurate scheduler (source complete, awaiting build)

- **Design refinement vs the plan (recorded per §0):** the plan sketched "loop-regime anchoring" to keep the tempo anchor single-writer. During implementation I found it unnecessary — `deriveBeat` is LINEAR in `mSamplePos`, so wrapping `mSamplePos` automatically yields the correct wrapped beat (`loopStartSamp` maps to `loopStartBeat` by construction; constant tempo = exact). So `advanceBlock` writes ONLY `mSamplePos` and never the anchor → the anchor stays cleanly single-writer (message thread: setBPM/seekTo/start/reset) with no special-casing, side-stepping the two-writer seqlock-corruption concern entirely. Tempo-change-while-looping self-heals via the next setBPM re-anchor (documented edge). Simpler + strictly safer than the plan's sketch.

## 2026-06-01 — Task 1 — verify pass 1 (tests 1-4 PASS; test 5 found 3 bugs; fixes landed)

- **Verify (Jeff, headset @ 44100/128):** tests 1-4 PASS. Test 5 (tempo automation) surfaced 3 issues. I had wrongly claimed (a) the audio was on time / only the piano-roll cursor was off, and (b) the Builder cursor wouldn't show it -- both wrong; owned + corrected.
- **Problem 2 (MAJOR, my QA-Ed regression) -- FIXED.** Under a mid-loop tempo change the loop wrapped early, the derived beat went negative, and each pass got shorter. Root cause: `advanceBlock` + the scheduler computed the loop's sample bounds as `llround(loopBeat*spb)` **from beat 0**, but the tempo anchor re-bases away from origin on a BPM change, so the from-zero bounds no longer mapped to the loop beats. Fix: measure `loopEndSamp`/`loopStartSamp` **relative to the current (sample, beat) point on the anchor line** -- `oldPos + llround((loopBeat - curBeat)*spb)` in `advanceBlock`, `samplePos + llround((loopBeat - beatStart)*spb)` in the scheduler. No-op at constant tempo (tests 1-4 unaffected). **Corrects the running-notes claim above that tempo-change-while-looping "self-heals" -- it did not; the plan's dropped "loop-regime anchoring" was needed, now solved this way.**
- **Problem 3 (automation doesn't follow the playhead) -- FIXED.** Jeff's spec: placing the playhead ANYWHERE should snap any param on an active automation to that automation's value at that beat (not just reset-to-0). `applyAutomationAtCurrentPosition` now applies on any playhead position change (playback OR a stopped seek/scrub) via `mLastAutomationBeat` change-detection, and applies APVTS lanes when STOPPED (the audio-thread automation pass only runs while playing). Skips only when stopped + static.
- **Problem 1 (Event Editor showed 0-1, no type-in) -- FIXED, for ALL params per Jeff + the JUCE tip.** Value readouts (footer + red value label) + a new right-click **"Set Value..."** type-in route through `EEAutomationGrid::onFormatValue`/`onParseValue`, wired in StandaloneEditor: APVTS lanes use the parameter's own `getText()`/`getValueForText()` (identical math to the knob + host automation); `global_tempo` is the one non-APVTS lane (20..300 BPM).
