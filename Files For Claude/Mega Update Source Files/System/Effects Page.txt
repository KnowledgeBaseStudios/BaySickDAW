4. Thread Safety (The Danger Zone)
In DAW development, the GUI runs on the message thread, and audio runs on a high-priority realtime thread. If the user swaps an effect while the processBlock is reading it, your DAW will crash.

Atomic Swapping: Never delete an effect on the audio thread, and never let the audio thread read an effect while it's being deleted.

The JUCE Way: Use juce::ReferenceCountedObject or manage a lock-free queue where the GUI thread passes the new effect to the audio thread. The audio thread safely swaps the pointer at the start of the next processBlock, and passes the old effect back to the GUI thread to be deleted.

A simpler alternative for early dev: You can use a juce::SpinLock (or juce::CriticalSection) inside the processBlock and when swapping effects, but be warned: locking the audio thread can cause audio dropouts (glitches) if the lock is held too long.

### Part 2: Dynamic Resizing for the Effects Page

Handling dynamic resizing in JUCE requires understanding that resizing cascades from the parent down to the children via the `resized()` callback. 

Because you are writing the source code for the internal effects going into these slots, you have a massive advantage: you can build your effect editors to be fully responsive rather than dealing with fixed-size, legacy 3rd-party VSTs.

Here is how you handle the layout and dynamic resizing so the effect UI perfectly fills the available space when the main window changes size.

#### Step 1: The Layout Logic
In your `EffectsPageComponent`, you use `getLocalBounds()` and JUCE's rectangle slicing methods to partition the screen.

```cpp
// Inside your EffectsPageComponent class
void EffectsPageComponent::resized()
{
    // 1. Get the total area of the Effects Tab
    auto area = getLocalBounds();

    // 2. Slice off the top for the track selector dropdown
    trackSelectorDropdown.setBounds(area.removeFromTop(40).reduced(5));

    // 3. Slice off the left side for the 6 effect slots
    rackPanel.setBounds(area.removeFromLeft(250).reduced(5));

    // 4. The remaining space goes entirely to the editor host
    editorHost.setBounds(area.reduced(5));

    // 5. CRITICAL: If the DAW window resizes, the host resizes.
    // We must tell the loaded plugin editor to resize to fit the new host size.
    if (auto* currentEditor = editorHost.getChildComponent(0))
    {
        currentEditor->setBounds(editorHost.getLocalBounds());
    }
}
```

#### Step 2: Loading and Sizing the Effect
When a user clicks on Slot 3, you clear the host, grab the new editor, and immediately force it to fit the current bounds of the host.

1. Global Architecture Standard
All effects in the rack must be built as decoupled C++ DSP classes. To ensure maximum performance and seamless integration into the audio engine, every module must follow this structural pattern:

No Plugin Wrappers: Do not use juce_add_plugin or VST/AU boilerplate. These are internal DAW components.

Decoupled DSP: Classes must follow the juce::dsp paradigm with three mandatory methods:

prepare(const juce::dsp::ProcessSpec& spec): Allocation and sample rate initialization.

process(const juce::dsp::ProcessContextReplacing<float>& context): The high-performance audio loop.

reset(): Clearing delay lines, envelopes, and filter histories.

Parameter Management: Each class should contain a public Parameters struct or dedicated setter methods. This allows the DAW engine to update DSP values from the UI thread safely.

UI Standards: All juce::AudioProcessorEditor components for these effects must use relative sizing (e.g., juce::FlexBox or juce::Grid) to ensure they scale correctly within the DAW's 6-slot rack interface.

The Slot: A container holding a std::unique_ptr<juce::AudioProcessor> and a bool isBypassed flag.

The Rack Processor: Iterates through the 6 slots during the processBlock. If a slot is active and not bypassed, it calls the effect's process method.
