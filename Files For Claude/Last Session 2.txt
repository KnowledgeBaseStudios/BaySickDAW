What are the differences between the two in terms of the end user experience?

From the end user's perspective, there's no meaningful difference in v1.9.

Both options produce the same visual experience: a graph inside Harmless where you draw envelopes and LFO shapes to modulate the synth's own parameters. The user draws a curve, it affects the sound, it saves with the preset.

The only scenario where the choice matters to a user is if you later want to link a Harmless internal envelope to the Builder's automation timeline — e.g. "this Harmless filter sweep syncs to bar position in the song." That would require shared types to work without a conversion layer.

But that's how FL Harmor actually works: its internal modulation is completely self-contained inside the instrument. The envelopes/LFOs you draw in Harmless modulate parameters per-note (they reset on each note trigger), while Builder automation operates over song position. These are fundamentally different domains — per-note modulation vs. arrangement-level automation. Sharing the same structs would imply they could be mixed, which is confusing to users.

Recommendation: define Harmless-internal structs. The user experience is identical for v1.9, the instrument stays self-contained like FL Harmor, and it avoids coupling Harmless preset data to the Builder's PatternManager. If song-synced modulation ever becomes a goal, that's a new feature with its own UI design — not a side effect of struct sharing.

What are benefits or negatives of this dependency and what are the benefits or negatives of having it's own internal struct?

Shared PatternManager types (dependency)
Benefits:

Zero duplication — one ControlPoint struct, one interpolation function (evaluateAt()), one serialization format
If you fix a bug or improve interpolation in the Builder's automation, Harmless gets it free
If you later add "song-sync mod" to Harmless, the plumbing is already there
Negatives:

HarmlessEditor.h pulls in PatternManager.h which pulls in everything PatternManager depends on — that's a wide include chain into a leaf-node instrument
If PatternManager's ControlPoint format ever needs to change for a Builder reason (adding a new field, changing serialization), you're touching Harmless at the same time — unrelated features become coupled change-sets
Harmless preset XML would embed PatternManager's serialization format — if that format ever changes, old Harmless presets could break even if Harmless itself didn't change
Makes Harmless un-portable: you can't pull the Harmless folder into another project without also bringing PatternManager
Internal Harmless struct
Benefits:

Harmless is fully self-contained — its mod data format is owned by the instrument and changes only when the instrument needs it
Harmless presets are independent: format changes in Builder never touch Harmless XML
Simpler includes — HarmlessEditor only depends on HarmlessProcessor
If you ever package Harmless as a standalone VST, it compiles cleanly
Negatives:

Some code duplication — you write a ControlPoint-equivalent struct and a small interpolation function that already exists in PatternManager

What are the differences between the two in terms of the end user experience?



From the end user's perspective, there's no meaningful difference in v1.9.

Both options produce the same visual experience: a graph inside Harmless where you draw envelopes and LFO shapes to modulate the synth's own parameters. The user draws a curve, it affects the sound, it saves with the preset.

The only scenario where the choice matters to a user is if you later want to link a Harmless internal envelope to the Builder's automation timeline — e.g. "this Harmless filter sweep syncs to bar position in the song." That would require shared types to work without a conversion layer.

But that's how FL Harmor actually works: its internal modulation is completely self-contained inside the instrument. The envelopes/LFOs you draw in Harmless modulate parameters per-note (they reset on each note trigger), while Builder automation operates over song position. These are fundamentally different domains — per-note modulation vs. arrangement-level automation. Sharing the same structs would imply they could be mixed, which is confusing to users.

Recommendation: define Harmless-internal structs. The user experience is identical for v1.9, the instrument stays self-contained like FL Harmor, and it avoids coupling Harmless preset data to the Builder's PatternManager. If song-synced modulation ever becomes a goal, that's a new feature with its own UI design — not a side effect of struct sharing.

What are benefits or negatives of this dependency and what are the benefits or negatives of having it's own internal struct?



Shared PatternManager types (dependency)
Benefits:

Zero duplication — one ControlPoint struct, one interpolation function (evaluateAt()), one serialization format
If you fix a bug or improve interpolation in the Builder's automation, Harmless gets it free
If you later add "song-sync mod" to Harmless, the plumbing is already there
Negatives:

HarmlessEditor.h pulls in PatternManager.h which pulls in everything PatternManager depends on — that's a wide include chain into a leaf-node instrument
If PatternManager's ControlPoint format ever needs to change for a Builder reason (adding a new field, changing serialization), you're touching Harmless at the same time — unrelated features become coupled change-sets
Harmless preset XML would embed PatternManager's serialization format — if that format ever changes, old Harmless presets could break even if Harmless itself didn't change
Makes Harmless un-portable: you can't pull the Harmless folder into another project without also bringing PatternManager
Internal Harmless struct
Benefits:

Harmless is fully self-contained — its mod data format is owned by the instrument and changes only when the instrument needs it
Harmless presets are independent: format changes in Builder never touch Harmless XML
Simpler includes — HarmlessEditor only depends on HarmlessProcessor
If you ever package Harmless as a standalone VST, it compiles cleanly
Negatives:

Some code duplication — you write a ControlPoint-equivalent struct and a small interpolation function that already exists in PatternManager
Two places to fix if a core interpolation bug appears (though in practice the Harmless mod graph is simpler than the full automation system — fewer curve types, no tension handles, so it's not the same code anyway)
The real question
PatternManager's ControlPoint has fields that Harmless's mod system doesn't need: CurveType, tension, tick-based timing (Harmless uses 0–1 normalized phase, not song ticks). So they're not actually the same struct — you'd be using ~60% of PatternManager's ControlPoint and ignoring the rest. That's the clearest signal to keep them separate: when you're already planning to ignore half the shared type, the "avoid duplication" benefit mostly evaporates.

Verdict: internal struct is the right call. The duplication is small, the isolation is worth it, and the types aren't actually equivalent.
